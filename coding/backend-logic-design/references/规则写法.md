# 规则写法

一条规则 = 编号 + 一句规则 + 一个案例 + 用户触点 + 状态（+ 出处）。规则写给开发和审核，案例写给用户。

## 字段

| 字段 | 要求 |
|---|---|
| 编号 | `后-NN`；给用户看过就不重排；作废的 status 改 `void`，编号不复用 |
| 规则 | 一句话说清「在什么情况下 → 系统怎么做」；有取值就写范围和超范围怎么办 |
| 案例 | 一个具体情景：谁（哪个模型 / 文件 / 页面）→ 做了什么 → 结果，用「→」串；最后一步是结果。新功能没真实事件时可以构造，`constructed: true` |
| 用户触点 | 有界面：前端状态编号（A1、C7）；没界面：`T1…`（验收页某一栏、停下时的消息、命令行输出），在 `touches` 里说明；确实没有：`无：理由` |
| 状态 | `confirmed` 这次设计期内向用户确认过 / `inherited` 以前用户亲口定过或签收过、这次没变 / `proposed` 计划或方案里写了、但用户没拍过板 / `pending` 待你定 / `ai` AI 定 / `void` 作废 |
| 出处 | `confirmed`、`inherited` 必填：用户原话 + 日期，或签收过的设计包位置；`proposed` 必填：写在哪份材料哪一节 |
| 确认时的正文 `confirmedText` | `confirmed` 必填：用户认可的那一版规则原文；正文之后改了字，要重新确认 |
| 步骤表 `steps` | 多步写操作必填，见下 |
| 时间轴 `timeline` | 时间类规则必填，见下 |

## 例子

好：

> **后-25** 某个模型已经给过意见，复审还找它。它被你关掉、连不上、超时时，换顺序里下一个能用、且不在这道关里正在审的模型当替补；替补接过它的意见和已用掉的轮次接着审。
> 案例：第一轮 DeepSeek 提了严重问题，改代码期间你在页面上关掉了 DeepSeek → 复审交给顺序里下一个 MiniMax，它拿到 DeepSeek 的意见和已用的 1 轮，接着审，最多再审 2 轮。
> 触点：验收页「审核」一栏 · 状态：confirmed · 出处：10-05 用户答第 3 题选 A

不好：

> 审核者不可用时进行 failover，保持 seat 连续性。

问题：术语、没说「不可用」包括哪些情况、没说替补拿到什么、没有案例。

## 两种特殊写法

**多步写操作 → 步骤表**（搬文件、先备份再删、先写 A 再写 B），写在规则的 `steps` 里：

| 步 step | 来自哪一版 from | 做之前 before | 做之后 after | 怎么验 verify | 断在这里怎么认出来 detect | 怎么倒回去 / 接着做 recover |
|---|---|---|---|---|---|---|
| 1 备份原件 | 点「收进」那一刻冻结的原件 | 原件在、无备份 | 原件在、有备份 | 备份和冻结版逐字节一致 | 有备份且原件未动 | 删备份即回到原状 |
| 2 写入资产库 | 第 1 步的备份 | … | … | … | … | … |

每一步还要问：
- 这一步进行中，原件被外部改了怎么办（不能用改过的原件覆盖备份，也不能删掉别人的新稿）；
- 备份 / 暂存的东西**写完立刻验**，验不过保留什么；
- 接着做时，范围有没有和第一次一样（不能悄悄扩大，第一次的例外——比如删库时只放回原件——要原样继承）；
- 反方向（撤回、恢复）也要一张表，不能只写正向。

**时间类规则 → 时间轴**（缓存、刷新、超时、日界），写在规则的 `timeline` 里：

> 从你新建文件那一刻算：0 秒 文件落盘 → 最多 30 秒内 下一次扫描发现 → 页面出现。窗口在后台时不扫，回到前台立刻扫一次。

有几个计时器就各写一根，按这个模板：

| 计时器 | 从什么时候开始算（起点） | 多久到点（时限） | 到点后怎么办 |
|---|---|---|---|
| 单条测试 | 这条开始跑 | 120 秒 | 结束这一条，记「超时」，接着跑下一条 |
| 单个文件 | 这个文件开始跑 | 3600 秒 | 结束这个文件，记「超时」 |
| 整轮 | 整轮开始 | 3600 秒 | 停下，已跑完的结果保留，没跑的标「没跑」 |

**谁先到点按「起点 + 时限」算绝对时刻，不按时限长短排**：整轮 0 秒开始、某文件第 60 秒开始、文件里某条第 3590 秒开始 → 三个截止时刻是 3600、3660、3710 秒 → 整轮最先到点。还要写**同时到点**时听谁的（一般是范围大的那个：整轮 > 文件 > 单条），以及到点后先停哪个、清理按什么顺序。

还要写清：哪些情况会提前 / 推迟、到点时清理动作不许把「超时」这个结果覆盖掉、跨午夜和时区怎么算。

## 卡片小例子的结果标记

`ok:` 正常结果（绿）、`stop:` 停下 / 失败（红）、`todo:` 还没定（橙）；不加前缀就是普通情景。别用单个字母当前缀（`x开头` 会吃掉 xhs-images 这种名字的首字母）。

## 常见的坑

- **一句话藏两条规则**：「保存失败回滚并重试」→ 拆开。
- **只写正常路径**：会写入或会失败的规则，都要写失败时怎样（或指向「⑥ 出问题时」的编号）。
- **「最多」「默认」「自动」含义不止一种**：用案例钉死。「最多 3 个」是「平时派 3 个」还是「上限 3 个、平时 1 个」，案例一写就露出来。
- **卡片说得比规则满**：规则允许断电后短暂不一致，卡片就不能写「永远一致」。
- **技术细节写进给用户看的规则**：字段名、路径、函数名只进附录。

## 状态怎么判断

| 是 `pending`（问用户） | 是 `proposed`（给用户过目） | 是 `ai`（一行通知） | 是 `inherited`（不问） |
|---|---|---|---|
| 两个结果都合理，取舍看用户偏好 | 计划 / 方案 / 讨论稿里写了，但找不到用户原话或签收 | 落实已定语义的保护：原子写、锁、校验、幂等、不放凭证 | 用户亲口定过、或签收过的设计包里有（含「AI 补」条目），这次没变 |
| 结果会让用户看到不同的东西、多花钱、多等待、数据去留不同 | AI 上一轮自己定的取舍 | 用户看不出区别 | 写出处；转述让另一家模型核一下有没有走样 |
| **技术改动改变了用户能感知的东西**：改默认值、改存放位置、改留存、把「真的」换成「假的」（如真实冒烟里用假模型） | | | |
| 新增的、用户能感知的规则（哪怕只有一个合理答案） | | | |
| 会推翻或扩大用户已定的事 | | | |

分不清「技术保护」还是「新增可感知规则」时这样问：**这条规则改变的是「怎么保证已经定的结果」，还是「用户会看到什么结果」？** 前者 `ai`，后者至少 `proposed`。例：「收进时备份和原件逐字节核对」保证已定的「不丢数据」→ `ai`；「收进中原件被外部改了，弹提示让你选保留哪份」是新的结果 → `pending`。
