# 回流模板（第 5 步：后端讨论发现前端要改）

交给前端设计（或 dev 正式版的根编排）的一页，至少写这些：

| 项 | 写什么 |
|---|---|
| 起因 | 哪条后端规则（`后-NN`）发现了什么，用一个时间线案例说清（例：09:00 点收进 → 09:01 备份完 → 09:02 你在编辑器里改了原件 → 搬走前核对发现变了） |
| 影响的前端内容 | 状态清单编号（如 C4②、C14）、交互流程哪一段、定稿文档哪一节、哪些文案；**前后差异**逐条列 |
| 候选做法 | 新状态 / 新提示的候选（新文案标「候选」），对应的业务题（带推荐） |
| 用户要看什么 | 只列改动的部分，让用户重点看；**签收仍是整份新版包**（插件按整包登记，没有局部签收） |
| 暂时的规则状态 | 相关规则保持 `pending`，`touch` 写「候选：W16」这类（`build.py` 只允许草稿里出现），不伪造已修已签 |
| 签收后要做的 | 用新的状态编号替换「候选：」触点，status 改 `confirmed`，写签收出处和 `confirmedText`；原审核者复核受影响规则；dev 正式版里由根编排重做受影响的需求对齐和业务确认 |

没有界面变化的纯技术保护（例：后端已经拦住了，只是多记一条日志）不回流，不动前端包。
